01
Engineering Philosophy

The principles behind every system I ship.

P1

Build boring before impressive

The data model, the integrity layer, and the tests come before any intelligent feature. Intelligence built on a shaky foundation is a demo — the boring work is what makes the impressive part survive production.

P2

Deterministic beats hopeful

I don't trust prompts or clients to be correct. Citations are validated deterministically, submissions are guarded by idempotency keys and atomic transactions, and an answer either traces to its sources or it doesn't ship.

P3

Test the failure path

Race conditions, cache outages, expired tokens, failed migrations — that's where systems break. 1,100+ automated tests cover auth, RBAC, concurrency, and data integrity, with fail-closed defaults when a dependency disappears.

P4

Measure, don't demo

A demo proves a system can work once; an evaluation harness proves it keeps working. Retrieval quality (Precision@1, MRR, Recall) and generation quality (Groundedness, Answer Correctness) are measured, not assumed.

P5

Design for the next engineer

Clear module boundaries, explicit interfaces, meaningful names, documented APIs. From Flask blueprints to layered backends, the codebase has to grow without becoming a burden for whoever touches it next.

P6

Own the whole path

Building isn't done until it ships. Docker, CI/CD, Linux, and cloud deployment close the gap between a system that works on my machine and one that stays reliable in production.

2026Backend · Reliability

The submission that arrived twice

When a student clicks submit twice — or a retry fires after a timeout — the exam must be graded exactly once. I placed the guarantee at the database level: database-backed idempotency keys, atomic transactions, and frozen attempt papers, so correctness never depends on the client behaving itself.

Outcome One-time submission guarantee · race conditions covered in the 1,100+ automated tests
2026Backend · Reliability

Choosing to fail closed

JWT revocation lives in Redis. When the cache is unreachable, do you fail open — letting requests through — or fail closed and reject them? We fail closed, with expiration-aware TTLs, because a few rejected requests cost far less than honoring a revoked token.

Outcome Fail-closed security behavior · cache-outage scenarios are in the test suite
2026AI & RAG

Grounded or nothing

A clinical answer that sounds right but cites nothing is worse than no answer. Every generation passes a deterministic citation-validation gate: claims must map back to retrieved sources before the response is allowed to ship.

Outcome 100% grounded responses · 130/130 candidate answers traceable to sources
2026AI · Reliability

Building the measuring stick

You can't tune what you don't measure. I built an evaluation harness covering retrieval (Precision@1, MRR, Candidate Recall) and generation (Groundedness, Answer Correctness, LLM-as-a-judge), so every pipeline change is compared against numbers instead of vibes.

Outcome 85% P@1 · 75% Answer Correctness baseline · every change measured against it
